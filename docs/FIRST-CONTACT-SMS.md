# Guarded first-contact SMS

The existing `preview_customer_message` accepts exactly one of `conversation_id` or `customer_id`. A customer-first preview resolves the verified existing customer and current phone, binds the exact body and customer version, and supports text only. Existing conversation replies/MMS retain their interface. No new tool, OAuth scope, credential, campaign or automatic AI response is created.

Execution uses the existing actor-bound, ten-minute MCP confirmation and atomic action claim. A server-only `mcp_first_message_attempts` ledger additionally serializes first-contact sends per normalized phone. The claim requires the current active owner, live `business:read`/`customer:contact` grant, unique customer identity, unchanged phone/version, no conversation appearing since preview, and no blacklist/opt-out. Customer data never supplies authorization.

There is no conversation or fictional sent message before provider acceptance. After Twilio supplies an SID, one transaction creates/reuses the truthful conversation, preserves racing inbound messages, appends the exact provider-confirmed text once, ensures the SMS log, and finalizes the attempt. New owner-started threads have AI disabled; this does not change existing threads or webhook subscriptions. No booking or price is changed.

Explicit provider rejection is recorded as rejected and returned as an error. Timeouts, 5xx, process crashes after claim and other ambiguous results stay blocked; neither the original key nor a new first-contact preview can resend that phone automatically. Normal MCP conversation sends also block a sending/unknown first-contact attempt. If a known rejection is corrected, only a distinct newly approved preview can claim again. Provider-accepted/history-pending errors retain the SID in the confirmation result and audit so operators can reconcile without resending. Reconciliation means inspecting that SID and ledger before finalizing the same attempt, never generating a new key to guess a retry.

Migration `20261026200429_add_guarded_first_customer_sms.sql` adds one private RLS ledger and two owner-bound service-role-only RPCs. Browser roles receive no table or RPC access; existing owner grants are unchanged. Apply this migration before deploying v1.7.1. Do not apply unrelated migrations.

This change supplies the guarded MCP/operator path. The older `/api/conversations/new` UI route remains unchanged and must not be used to evade first-contact send controls. It does not provide these durable idempotency/provider-outcome guarantees. Native clients may retain older tool schemas; the already-authorized operator service can use the released `previewConversationSend` and `executePreparedAction` functions without new access while metadata refresh is pending.

Verification: 146 tests in 26 selected suites, 15 synthetic database scenarios, two true independent-session PostgreSQL concurrency cases, types, targeted lint and local production build pass. Tests use synthetic data and never call a real sender. The database fixture includes existing contact triggers and confirms no duplicate conversation/message/SMS log on concurrent finalization. No production success is claimed until the exact deployed commit and real authorized SMS outcome are separately read back.

Rollback: stop invoking customer-first previews and roll back application code if necessary. Preserve the private attempt/audit ledger, especially sending/unknown outcomes; do not drop it or unlock retries as a substitute for provider reconciliation. No permission removal or webhook change is needed.
