# Sasquatch Sightings MCP operations coverage

This inventory maps the existing Sightings application to the remote MCP adapter. It is deliberately explicit about side effects: a workflow existing in Sightings does not mean an MCP client is authorized to run it.

Status meanings:

- **Implemented** — exposed through the current read-only MCP and covered by MCP discovery/schema tests.
- **Partial** — useful read coverage exists, but the full screen/workflow is not exposed.
- **Existing, not exposed** — Sightings implements the workflow; MCP does not.
- **Blocked/missing** — a safe adapter needs a shared service, scope, approval, or canonical source that does not yet exist.
- **Outside scope** — intentionally excluded from this business-operations MCP.

All implemented tools require the existing OAuth owner grant and `business:read`. They perform no mutations and use `readOnlyHint: true`. Proposed scopes below are design placeholders only; they are not advertised by the live authorization server.

## Current tool contract

The original seven names and schemas remain backward compatible:

`list_appointments`, `get_appointment`, `list_estimates`, `get_estimate`, `search_customers`, `get_availability`, `list_calls`.

The operations visibility layer adds:

`get_capability_catalog`, `get_business_configuration`, `search_business_records`, `get_operational_summary`.

The MCP server identity remains `sasquatch-sightings-read`, and the endpoint remains `/mcp`. No production deployment or OAuth scope expansion is part of this change.

## Approval boundary for a future mutation phase

Before any mutation tool is implemented, the remaining (truncated) requirements need to be supplied or confirmed. The defaults discussed with Charles are proposals, not authorization. Price/catalog administration, business-hours/security administration, destructive record deletion, charges, refunds, and payment recording remain permanently unavailable to Dot. Any separately approved mutation handler must call an existing shared domain service, validate the OAuth subject/scope and record authorization server-side, accept an idempotency key, return a preview where feasible, and require action-time confirmation for customer contact or schedule commitments. MCP annotations are descriptive and must not substitute for those controls.
